IM APPSDEV BACKEND REVIEWER
===========================

Project: Lost and Found Item Management API
Backend: Laravel 12
Authentication: Laravel Sanctum personal access tokens
Database: MySQL in Docker, SQLite in tests


1. PROJECT STRUCTURE
====================

backend/
  app/
    Http/Controllers/       API request handling
    Http/Middleware/        Authentication and admin authorization
    Models/                 Eloquent database models
  bootstrap/app.php         Laravel 12 middleware aliases
  config/                   Application configuration
  database/migrations/      Database table definitions
  database/seeders/         Default database data
  routes/web.php            API routes used by this project
  storage/app/public/       Public uploaded files
  tests/Feature/            Feature and endpoint tests

Important files:

- routes/web.php
  Contains authentication, category, item, claim, dashboard, and status routes.

- app/Http/Controllers/
  Contains the logic for each API feature.

- app/Models/
  Contains the Eloquent relationships and mass-assignable fields.

- bootstrap/app.php
  Registers the admin middleware alias:

    'admin' => EnsureUserIsAdmin::class

3. AUTHENTICATION
=================

Authentication uses Laravel Sanctum bearer tokens.

Register:

  POST /register

JSON body:

  {
    "name": "Jane Doe",
    "email": "jane@example.com",
    "password": "password123",
    "password_confirmation": "password123"
  }

The response includes:

- user
- token

The user role defaults to user. The role is not mass assignable during registration, so a normal user cannot register as admin.

Login:

  POST /login

JSON body:

  {
    "email": "jane@example.com",
    "password": "password123"
  }

Use the returned token on protected requests:

  Authorization: Bearer YOUR_TOKEN_HERE

Current user:

  GET /user

Requires a valid bearer token.

Logout:

  POST /logout

Requires a valid bearer token. The current Sanctum token is deleted/revoked.

Authentication model behavior:

- User uses Laravel Sanctum HasApiTokens.
- Passwords are automatically hashed through the User model cast.
- Password and remember_token are hidden from JSON output.


4. ROLES AND ADMIN AUTHORIZATION
================================

Users have a role column:

  user
  admin

Admin-only routes use:

  auth:sanctum
  admin

The admin middleware checks:

  $request->user()->role === 'admin'

Non-admin users receive HTTP 403:

  {
    "message": "Admin access is required."
  }

The role is intentionally excluded from User::$fillable. To create an admin in development, update the database directly or use a seeder/factory state.

Example Tinker command:

  php artisan tinker --execute "App\\Models\\User::where('email', 'admin@example.com')->update(['role' => 'admin']);"


5. CATEGORIES
=============

Categories are created before items because both lost and found items require category_id.

Default seeded categories:

- Electronics
- Wallet
- ID Card
- Bag
- School Supplies
- Others

Public category routes:

  GET /categories
  GET /categories/{category}

Admin category routes:

  POST   /categories
  PUT    /categories/{category}
  DELETE /categories/{category}

Create category body:

  {
    "name": "Documents"
  }

Category names are unique.

The CategorySeeder uses an idempotent upsert, so running the seeder repeatedly does not create duplicate default categories.


6. LOST ITEMS
=============

User routes:

  GET    /lost-items
  POST   /lost-items
  GET    /lost-items/{lostItem}
  PUT    /lost-items/{lostItem}
  PATCH  /lost-items/{lostItem}
  DELETE /lost-items/{lostItem}

User behavior:

- Users can view only their own lost-item list.
- Users can view, edit, and delete only their own reports.
- Every lost item belongs to a user and category.
- New lost reports start with status lost.

Create lost item JSON example without an image:

  {
    "category_id": 2,
    "title": "Black wallet",
    "description": "Leather wallet with identification cards.",
    "location_lost": "Library",
    "date_lost": "2026-09-10"
  }

Admin routes:

  GET    /admin/lost-items
  DELETE /admin/lost-items/{lostItem}
  PATCH  /admin/lost-items/{lostItem}/status

Admin can view all lost reports and delete invalid reports.

8. SEARCH AND FILTERING
=======================

Unified public search endpoint:

  GET /items

Available query parameters:

- search
  Searches title and description.

- category
  Partial, case-insensitive category name search.

- date
  Exact item date. Lost items use date_lost; found items use date_found.

- location
  Partial location search. Lost items use location_lost; found items use location_found.

- status
  Filters by lifecycle status.

Examples:

  GET /items?search=wallet
  GET /items?category=electronics
  GET /items?date=2026-09-10
  GET /items?location=library
  GET /items?status=lost

Filters can be combined:

  GET /items?search=wallet&category=wallet&status=lost

The response normalizes both item types to common fields:

- id
- type
- user_id
- category
- title
- description
- location
- date
- image
- status
- created_at
- updated_at


9. CLAIMS
=========

Claims are connected to found items through found_item_id.

A user submits a claim when they believe a found item belongs to them.

User routes:

  POST /found-items/{foundItem}/claims
  GET  /claims
  GET  /claims/{claim}

Submit claim JSON example without proof image:

  {
    "claim_reason": "I believe this wallet belongs to me.",
    "proof": null
  }

Rules:

- A user cannot claim their own found item.
- A user cannot have multiple active pending/approved claims for the same found item.
- New claims start with status pending.
- Claim proof can be uploaded as an image.

Admin routes:

  GET  /admin/claims
  GET  /admin/claims/{claim}
  POST /admin/claims/{claim}/approve
  POST /admin/claims/{claim}/reject

Admin workflow:

  Claim Submitted
        |
        v
  Review Claim
        |
        v
  Verify Details
        |
        +--> Approve
        |
        +--> Reject

Claim statuses:

- pending
- approved
- rejected

Approving a claim changes the related found item status to claimed.


10. ITEM STATUS LIFECYCLE
=========================

Normal lifecycle:

  Lost -> Found -> Claimed -> Verified -> Returned

Rejected branch:

  Lost or Found or Claimed or Verified -> Rejected -> Closed

Other valid close paths:

  Lost -> Closed
  Found -> Closed
  Claimed -> Closed
  Verified -> Closed

Terminal statuses:

- returned
- closed

Once an item is returned or closed, it cannot transition again.

Admin status endpoints:

  PATCH /admin/lost-items/{lostItem}/status
  PATCH /admin/found-items/{foundItem}/status

Request body:

  {
    "status": "verified"
  }

Allowed transitions are checked by ItemStatusController. Invalid transitions return HTTP 422.

Examples:

  PATCH /admin/found-items/12/status
  {
    "status": "claimed"
  }

  PATCH /admin/found-items/12/status
  {
    "status": "verified"
  }

  PATCH /admin/found-items/12/status
  {
    "status": "returned"
  }


11. IMAGE UPLOADS
=================

Image uploads use multipart/form-data, not JSON.

Supported upload types:

- Lost item image
- Found item image
- Claim proof image

Validation:

- image file required when supplied
- jpg, jpeg, png, or webp
- maximum size: 5 MB

Storage directories:

  storage/app/public/lost-items
  storage/app/public/found-items
  storage/app/public/claim-proofs

The database stores the relative path, for example:

  lost-items/abc123.jpg

The file is not stored in source control. It is stored on the backend filesystem.

Create lost item with image using Postman:

- Method: POST
- URL: http://localhost:8000/lost-items
- Body: form-data
- Add normal text fields.
- Add image field with type File.
- Add Authorization bearer token.

Example form-data fields:

  category_id    Text    2
  title          Text    Black wallet
  description    Text    Leather wallet
  location_lost  Text    Library
  date_lost      Text    2026-09-10
  image          File    wallet.jpg

Create found item with image:

  POST /found-items

Use the same multipart approach, but use location_found and date_found.

Submit claim proof image:

  POST /found-items/{foundItem}/claims

Form-data fields:

  claim_reason   Text    I believe this wallet belongs to me.
  proof          File    proof.jpg

Public access:

  /storage/lost-items/filename.jpg
  /storage/found-items/filename.jpg
  /storage/claim-proofs/filename.jpg

The public storage symlink is created with:

  php artisan storage:link --force

Never commit user-uploaded files to Git.


12. ADMIN DASHBOARD STATISTICS
==============================

Admin endpoint:

  GET /admin/dashboard/statistics

Response contains simple counts only:

  {
    "total_users": 10,
    "total_lost_items": 8,
    "total_found_items": 6,
    "pending_claims": 2,
    "returned_items": 3
  }

Definitions:

- total_users: count of users in users table.
- total_lost_items: count of lost_items table rows.
- total_found_items: count of found_items table rows.
- pending_claims: claims with status pending.
- returned_items: lost and found items with status returned combined.

This endpoint requires both Sanctum authentication and admin authorization.


13. DATABASE RELATIONSHIPS
==========================

User:

- hasMany LostItem
- hasMany FoundItem
- hasMany Claim

Category:

- hasMany LostItem
- hasMany FoundItem

LostItem:

- belongsTo User
- belongsTo Category

FoundItem:

- belongsTo User
- belongsTo Category
- Claims belong to the found item through Claim's found_item_id relationship

Claim:

- belongsTo User
- belongsTo FoundItem

Important foreign keys:

- lost_items.user_id -> users.id
- lost_items.category_id -> categories.id
- found_items.user_id -> users.id
- found_items.category_id -> categories.id
- claims.user_id -> users.id
- claims.found_item_id -> found_items.id


14. COMMON API STATUS CODES
===========================

200 OK

Request succeeded.

201 Created

A new resource was created.

401 Unauthorized

No valid authentication token was supplied.

403 Forbidden

The user is authenticated but does not own the resource or is not an admin.

404 Not Found

The requested model does not exist.

422 Unprocessable Entity

Validation failed or a requested status transition is invalid.
